# Change Log — 2026-09-08: AIOps Pipeline Fixes & Server Setup

## Part 1 — Why these changes were needed

1. **The AIOps monitoring chain was dead on arrival.** The README promised a
   `configs/prometheus.yml` that did not exist, Prometheus scraped nothing,
   and the AI metric file written by `ai_monitor.py` was never read by any
   collector.
2. **The Big-AGI UI could not reach Ollama** because its config pointed at
   `localhost` from inside a container.
3. **`ERR_CONNECTION_REFUSED` on `http://localhost:11434/`**: Ollama was not
   installed on this server at all — no binary, no systemd unit, nothing
   listening on port 11434.
4. **Network constraint discovered during setup:** this host's route to
   GitHub (and `ollama.com`, which redirects there) and Docker Hub is
   throttled to < 50 KB/s, while other CDNs (Cloudflare) run at multi-MB/s
   speeds. See Part 4 for the workaround used.

## Part 3 — Host/system changes (fixing the connection-refused error)

These were made directly on this server (Ubuntu, `sudo` available) and are
not version-controlled:

### 3.1 Ollama v0.33.3 installed
- Official `install.sh` abandoned after it stalled at < 50 KB/s on the
  throttled GitHub route.
- Instead: downloaded the official release asset
  `ollama-linux-amd64.tar.zst` (1.43 GB, v0.33.3) via a GitHub mirror proxy
  (`gh-proxy.com`, ~4 MB/s), verified the tarball, extracted:
  ```bash
  sudo tar --zstd -xf /tmp/ollama-linux-amd64.tar.zst -C /usr/local
  ```
  → `/usr/local/bin/ollama` + `/usr/local/lib/ollama/` (CUDA/runner libs).
- Temp tarball deleted after install.

### 3.2 System user
```bash
sudo useradd -r -s /bin/false -m -d /usr/share/ollama ollama
```
Owns `/usr/share/ollama/.ollama` (the model store).

### 3.3 Systemd unit `/etc/systemd/system/ollama.service` (NEW)
```ini
[Unit]
Description=Ollama Service
After=network-online.target

[Service]
ExecStart=/usr/local/bin/ollama serve
User=ollama
Group=ollama
Restart=always
RestartSec=3
Environment="OLLAMA_HOST=0.0.0.0:11434"
Environment="OLLAMA_ORIGINS=*"

[Install]
WantedBy=default.target
```
Enabled and started: `sudo systemctl enable --now ollama`.

This implements the README's troubleshooting requirements
(`OLLAMA_HOST` on all interfaces, `OLLAMA_ORIGINS="*"`).

### 3.4 Model pulled
`ollama pull deepseek-coder:1.3b` — 776 MB, pulled from the Ollama registry
(the registry route was not throttled).

## Part 4 — Network constraint & workaround (for future installs)

Symptom: `github.com`, `ollama.com`, and Docker Hub downloads proceed at
< 50 KB/s from this host, while Cloudflare-fronted endpoints run at ~3.5 MB/s.
This is a route/peering issue on the local network, not a general outage.

Workaround that worked:
1. Resolve the desired asset URL from the GitHub API.
2. Prefix it with a GitHub release mirror (e.g. `https://gh-proxy.com/`).
3. Pull the Ollama model itself normally — `registry.ollama.ai` is not
   affected.

If Docker Hub images (`prometheus`, `grafana`, the UI images) pull too
slowly, use a registry mirror (e.g. configure `registry-mirrors` in
`/etc/docker/daemon.json`) or pull during a window when the route recovers.

## Part 7 — AI gateway: centralized monitoring & auditing (same day)

Goal: put a controlled endpoint in front of Ollama so every user/application
is identified and every prompt, response, model, duration and error is
captured and searchable centrally in Grafana.

### What was built

**`gateway/app.py`** — stdlib-only Python reverse proxy on `:11435`.
- Auth: per-user API keys from `gateway/users.json` (gitignored; template in
  `users.json.example`) via `Authorization: Bearer`, `X-API-Key`, HTTP Basic,
  or `?key=` for header-less UIs. 401 without a valid key.
- Audit: one JSON line per request in `monitoring/logs/gateway_audit.jsonl` —
  user, team, path, model, prompt & response (truncated to 4 KB), HTTP status,
  duration, token usage (`eval_count`, `prompt_eval_count`, `total_duration`).
  Upstream failures are audited as 502s.
- Metrics: `/metrics` exposes `ai_gateway_requests_total{user,model,path,status}`
  and a `ai_gateway_request_duration_seconds` p50/p95 summary.
- Forwards everything else (incl. `/api/chat`, `/api/tags`, `/api/version`)
  to Ollama; `/health` for liveness. Users file hot-reloads on mtime change.

**`gateway/ollama-gateway.service`** — systemd unit, `Restart=always`,
enabled at boot, running now (`systemctl status ollama-gateway`).

**Observability stack (`monitoring/`)**:
- `docker-compose.yml` + **Loki** (`:3100`, filesystem storage, 720 h
  retention) and **Alloy**; Grafana now loads `grafana/provisioning/`.
- `alloy/config.alloy` — tails `/var/log/gateway/*.jsonl`, JSON-parses,
  labels each line by `user`/`model`/`path`/`status`, pushes to Loki.
- `loki/config.yaml` — tsdb schema v13, auth off (LAN), 30-day retention.
- `grafana/provisioning/datasources/datasources.yml` — Prometheus + Loki.
- `grafana/provisioning/dashboards/ai-activity.json` — **AI Activity**
  dashboard: requests by user, requests by model, non-2xx error rate,
  p50/p95 latency, tokens per model (LogQL `unwrap usage_eval_count`),
  and a raw audit-log search panel.
- `prometheus.yml` — new `ai-gateway` job scraping `host.docker.internal:11435`.
- `.gitignore` — `monitoring/logs/*` and `gateway/users.json` never committed.

**UI rewiring (`uis/docker-compose.yml`)** — all three UIs now point at
`http://host.docker.internal:11435?key=ui-*` instead of Ollama directly, so
chat traffic is audited with a per-UI identity.

### Verification (live, 2026-09-08)
- 401 without key; 200 + audited generation with key; query-param key works.
- `gateway_audit.jsonl` records user/team/model/prompt/response/usage.
- Prometheus target `ai-gateway` **up**; `ai_gateway_requests_total` queryable.
- Alloy tails the JSONL; Loki returns all audit streams labeled by user/model;
  the tokens LogQL in the dashboard returns live values.
- Grafana `:4000` shows both datasources and the AI Activity dashboard.

### Known limitations
- Plaintext HTTP on the LAN; keys are bearer secrets.
- `ollama` CLI and the AIOps bridge still hit Ollama on `:11434` directly
  (intentional for the bridge — avoids an audit feedback loop).
- Gateway metrics use an in-memory rolling sample for latency quantiles, so
  p50/p95 reset on restart.
